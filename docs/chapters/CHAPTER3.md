# 3 METHODOLOGY

This chapter describes how NeuroScan was developed and how it was evaluated. Section 3.1 lists the software, hardware, and data used; Section 3.2 states the research design, the process model followed, the procedures and system models produced across the phases of development, and the evaluation plan applied to the model and to the application.

## 3.1 Materials

### 3.1.1 Software

Development proceeded in two software environments that meet at the exported model: a Python pipeline in which the convolutional neural network is trained and evaluated, and the Windows desktop application in which that model is executed. The Python side is built on Python 3.14 with PyTorch and torchvision for model definition, training, and evaluation, and its dependencies are resolved into an isolated environment by `uv`. Because the application must not require a Python installation on the machine of an end user, the trained network is exported to ONNX, an open format for representing machine learning models that defines a common set of operators and a common file format so that a model can be used with a variety of frameworks, tools, runtimes, and compilers ([ONNX, n.d.](https://onnx.ai/)). Inference inside the application is performed by ONNX Runtime, a cross-platform machine learning model accelerator that can be used with models exported from PyTorch and other frameworks, and whose documented pattern is to train in Python and deploy into a native C#/C++/Java application ([ONNX Runtime, n.d.](https://onnxruntime.ai/docs/)). The same documentation places responsibility for validating the accuracy, performance, and suitability of a deployed model on the model's developer, which is why the parity and evaluation procedures in §3.2.3 and §3.2.4 are treated as part of the development rather than as optional checks.

The application itself is built with Tauri 2, which hosts a React and TypeScript frontend inside the Windows WebView2 control and pairs it with a Rust backend. The Rust backend is where the screening work happens: the `ort` crate binds ONNX Runtime for inference, the `image` crate decodes and resizes the MRI images and composites the heatmap overlay, `ndarray` handles tensor input and output, `serde` and `serde_json` handle the persisted history and the model's configuration record, and the dialog and file-system plugins provide the native folder pickers used for opening folders and choosing export destinations. The frontend is scaffolded with Vite following the conventions of Tauri's application template, and the frontend toolchain runs on Node 24 with npm. The application is compiled with the stable Rust toolchain for MSVC. Version control is handled with Git.

Running the model inside the application rather than on a server is a deliberate design choice rather than a technical convenience. Analysis performed in the cloud requires that patient information cross a network, which raises privacy concerns together with security and regulatory barriers, and bespoke desktop software imposes its own costs in the form of administrative and security approval and per-device configuration; the reviewed literature also notes that clinical workstations typically lack graphics processing units ([Dong et al., 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10099365/)). NeuroScan accepts the installation and configuration costs of desktop software in exchange for keeping every image on the machine that already holds it, and the absence of a graphics processor on the target hardware is the constraint that shapes the model and the memory design described in §3.1.2.

### 3.1.2 Hardware

Model development and testing were carried out on a Windows machine with a 12th Generation Intel Core i5-12450H processor (eight logical cores) and 8 GB of memory, with integrated Intel UHD graphics and no discrete NVIDIA processor. Because the machine has no CUDA-capable device, full fine-tuning of a pre-trained backbone was performed on a cloud GPU runtime, with the training script detecting the available device automatically; the local processor was used for smoke runs of the training pipeline, for evaluation, and for the parity checks described in §3.2.3.5, and the small fallback network trains locally in minutes. This division is a consequence of the available hardware rather than a general recommendation, and it does not affect the shipped application, which performs no network access at screening time.

The application is intended for an ordinary Windows desktop or laptop without a discrete graphics processor, which is the hardware profile reported for clinical workstations ([Dong et al., 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10099365/)) and the setting in which lightweight architectures are held to be practical ([Kantu et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13103188/)). This target imposes two constraints on the design. First, the deployed model must be light enough to run acceptably on a processor alone, which is why the study adopts the lightweight-architecture direction documented in the reviewed deployment literature rather than a computationally intensive backbone ([Kantu et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13103188/)). Second, memory use must remain within what an 8 GB machine can sustain, so batch screening decodes one image at a time, resizes it immediately, and discards the full-resolution copy before the next file is read, with a peak memory target below approximately 2 GB.

### 3.1.3 Data

The study uses two publicly available, labeled datasets of two-dimensional brain magnetic resonance images, both obtained from Kaggle in 2026 through the platform's public archive download endpoints without authentication, with each download checked against a recorded byte size, tested for archive integrity, and retried once on transient failure. The first is the Br35H dataset, whose own record documents three folders — `yes`, `no`, and `pred` — containing 3,060 brain MRI images, of which the `yes` folder holds 1,500 tumorous and the `no` folder 1,500 non-tumorous images ([Hamada, 2020](https://www.kaggle.com/datasets/ahmedhamada0/brain-tumor-detection)). The study uses the 1,500 tumorous and 1,500 non-tumorous images as the balanced binary source and does not use the unlabeled `pred` folder. The record carries the license string "Data files © Original Authors" and was last updated on 14 November 2021.

The second is the Brain Tumor MRI dataset, whose record documents four classes — glioma, meningioma, pituitary tumor, and no tumor — and states that version 2 of the dataset contains 7,200 images with balanced classes, arranged as 1,400 training and 400 testing images per class, having removed duplicate images and eliminated overlap between its training and testing sets to prevent data leakage ([Nickparvar, 2026](https://www.kaggle.com/datasets/masoudnickparvar/brain-tumor-mri-dataset)). The same record states that the no tumor class was sourced from the Br35H dataset, and that the collection is a curated combination of the figshare brain MRI dataset, the SARTAJ dataset, and Br35H, in which glioma images from SARTAJ were replaced with images from figshare during preparation because of label inconsistencies. The record's license is Attribution 4.0 International (CC BY 4.0), and like the first dataset it documents the composition and licensing of the images but not the scanners or acquisition protocols behind them.

The two sources do not agree with the literature on the size of the second dataset. A study that evaluated lightweight architectures on this dataset reports it as comprising 7,023 images, with 1,621 glioma, 1,645 meningioma, 2,000 no-tumor, and 1,757 pituitary images, split into 4,522 training, 1,186 validation, and 1,311 test images ([Kantu et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13103188/)). Those figures describe an earlier version of the same dataset record, which now documents version 2 and its 7,200 images. Both figures are therefore reported here rather than one being preferred, and the number of images the pipeline actually processed is taken from the run's own manifest rather than from either published figure, because it depends on how many exact duplicates the union of the two sources is found to contain.

The pipeline built for the study treats the datasets as follows. Both archives are merged into one working set, and exact duplicates are removed by content hash — the SHA-256 digest of the decoded pixels — before any split is made. This step is mandatory rather than precautionary: because the no tumor class of the Brain Tumor MRI dataset was sourced from Br35H ([Nickparvar, 2026](https://www.kaggle.com/datasets/masoudnickparvar/brain-tumor-mri-dataset)), identical images would otherwise be present in both sources, and without deduplication they would straddle the training and test partitions and inflate the reported accuracy. The measure is also consistent with the finding that earlier work in this area has introduced data leakage through augmented test sets and unstandardized dataset splits ([Kantu et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13103188/)). Near-duplicate analysis is out of scope for this study. After deduplication, the three tumor classes are collapsed into a single positive class so that the task is binary, while each image's original fine label and contributing source are retained in a manifest, so that the same downloads can be reused if the study is later extended to four-class classification. The merged binary set is then split into training, validation, and test partitions in a stratified and seeded manner, and because collapsing the classes produces a set in which tumor images outnumber no-tumor images by roughly seven to three, training applies class-balanced sampling together with a weighted loss. The test partition is set aside at this point and is used neither for training nor for selecting the decision threshold.

Two limitations follow from the data rather than from the implementation, and they are stated here so that the scope of the results is clear. The images are individual two-dimensional slices with one label each, drawn from public benchmark collections rather than from the records of a hospital, so the class labels represent the datasets' own annotations and have not been confirmed by a second reader. And because the records do not document the scanners or protocols behind the images, variation in acquisition across scanners cannot be controlled or measured. The study uses no clinical data and no human participants, so no ethics review was required; the constraints that remain are discussed with the evaluation in §3.2.4.

## 3.2 Methods

### 3.2.1 Research Design

This study employs a developmental research design: it designs, builds, and evaluates a working artifact, the NeuroScan screening application, rather than describing a phenomenon that already exists. The structure of the work follows design science research, which is a problem-solving paradigm in which knowledge is created by designing and building artifacts that embody prescriptive knowledge about solving a class of problems, and in which an instantiation — the actual functioning system, as opposed to a model or a method — is itself the object of evaluation ([Dyers et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13150388/)). Adopting that orientation commits the study to two outputs rather than one: the prototype itself, and the design knowledge that can be transferred from it, which is why the preprocessing constants, the exported model interface, and the pipeline's partitioning rules are documented in this chapter as reusable artifacts rather than left implicit in the code.

The design is problem-oriented in the sense that the gap it addresses was established before any component was built. Two review-level findings frame it: a meta-analysis of explainable clinical decision support research found an absence of studies evaluating explanation fidelity, clinician trust, or usability in real-world settings ([Abbas et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12427955/)), and a systematic review of CNN-based brain tumor classification studies concluded that few such studies had focused on clinical usability at all ([Xie et al., 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC9406354/)). NeuroScan therefore answers a question the model-centric literature leaves open — how a trained classifier is delivered to the person who would use it — and does so under a further constraint identified in the deployment literature, that images should not cross a network ([Dong et al., 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10099365/)).

The role the system is designed to play in a workflow also determines what it is optimized for. In image interpretation, a model used in practice acts as a concurrent aid, a second reader, or a pre-screening filter, and in each case the clinician remains the decision-maker ([Chen et al., 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11608314/)). NeuroScan is designed as the pre-screening kind: it orders and prioritizes images and shows its reasoning, but it does not diagnose, and clinician review lies outside the system boundary. Three design priorities follow from that role — a low tolerance for missed tumors, an explanation attached to the individual prediction, and local execution — and they are the reasons for the sensitivity-first threshold, the class activation mapping heatmap, and the offline architecture described in the sections below.

The evaluation stance is also part of the design. Design science research distinguishes evaluation that is formative from evaluation that is summative, and evaluation conducted in artificial settings from evaluation conducted in naturalistic ones ([Dyers et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13150388/)). Both forms of assessment carried out in this study are summative and artificial: the model is measured on a held-out partition of public benchmark data, and the prototype is assessed against test cases rather than in a clinical setting. The study therefore evaluates whether the artifact meets its stated objectives; it does not establish clinical validity, and no claim of diagnostic accuracy in practice is made.

### 3.2.2 Process Model

Development followed an iterative and incremental model, organized as a sequence of milestone phases, each with exit criteria that had to be met before the next phase began. Iteration rather than single-pass development is appropriate here because design science research treats build–evaluate cycles as the mechanism through which both the artifact and the understanding of it improve, particularly where requirements emerge through use rather than being fully specified in advance ([Dyers et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC13150388/)). The phases were defined as follows.

1. **Repository bootstrap.** The project layout, ignore rules, and readme were established and the specification committed, so that every later phase had a documented target.
2. **Data preparation.** The download, integrity-check, deduplication, binary collapse, and stratified partitioning steps produced the processed dataset together with its manifest.
3. **Training and export.** A pre-trained backbone was fine-tuned and evaluated, and the export step produced the ONNX model together with its configuration record.
4. **Application scaffold and inference.** The Tauri application was built, the bundled model was loaded through the inference core, and the Python and Rust paths were shown to agree on a set of sample images.
5. **Heatmap.** Class activation mapping was computed in the application from the exported head weights and rendered over the source image.
6. **Batch, history, and export.** Folder screening with live progress, the persisted screening history, and the CSV and annotated image exports were completed.
7. **Packaging.** The Windows installer was produced, the disclaimer text was reviewed in every view, and the readme was finalized.

The phases above track progress rather than delimiting staged deliveries: the objective of the study is the complete usable application, so the work was planned as one continuous build with the milestones serving as checkpoints and as the order in which the components depend on one another. Three verification activities run across all phases rather than belonging to any one of them. Determinism is maintained by fixed random seeds, a saved run configuration, and versioned checkpoints, so that a reported result can be traced to the exact model and settings that produced it. Parity between the two inference paths is tested whenever preprocessing or the export contract changes, as described in §3.2.3.5. And each milestone's exit criteria function as an internal review, so a defect is detected in the phase that introduced it rather than at the end of the project. Figure 3-1 presents this process.

#### 3.2.3.3 System Architecture

The architecture separates work performed at development time from work performed at run time, and the boundary between them is the exported model file. At development time, a Python pipeline downloads and verifies the sources, deduplicates and partitions the data, trains and evaluates the network, and exports the ONNX model together with a configuration record that fixes the input size, the normalization constants, the class order, and the screening threshold. At run time, the Tauri application hosts a React frontend inside WebView2 and a Rust backend that performs all image and inference work; the frontend invokes backend commands and receives batch progress through events, and the model and its configuration ship inside the installer as application resources, located through the shell's resource resolver rather than by a current-directory lookup. The inference core is a single pipeline shared by the single-image and batch paths, so that a folder scan and a manual scan preprocess and classify an image identically.

The design deliberately maintains one runtime inference path and treats the Python side as a development and validation surface rather than as an alternative runtime. This avoids the failure mode in which two implementations of the same preprocessing diverge and produce different predictions for the same image; the Python implementation exists to train the model and to verify the Rust implementation against it.

#### 3.2.3.4 Screening Process Flowchart

Screening an image follows a fixed sequence. The image is decoded, with single-channel images replicated to three channels, any alpha channel dropped, and any EXIF orientation applied, so that a grayscale MRI and a color copy of the same scan are treated alike. The decoded image is resized to 224 × 224 pixels by bilinear interpolation, scaled to the unit range, normalized with the statistics of the pre-trained backbone, and arranged into a single four-dimensional tensor. One forward pass through the exported model then yields the class logits, the final convolutional feature map, and the head weight matrix. The logits are converted to a probability by the softmax function, and that probability is compared with the screening threshold. A probability at or above the threshold yields a tumor verdict and one below it yields a no-tumor verdict, except within a narrow band either side of the threshold, where the result is presented as low confidence and referred for manual review rather than shown as a decision. The heatmap is computed from the same forward pass: for the predicted class, the feature map is combined with that class's weights from the head matrix, the negative values are discarded, the result is resized to the input resolution, normalized to the full range of intensities, assigned a color map, and composited over the source image.

Class activation mapping in this application is the visualization technique that generates a heatmap highlighting the regions of an input image that contribute most to a specific class prediction ([Nazir et al., 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11497403/)), and it is computed from the head weights rather than by backpropagation because inference through ONNX Runtime provides no gradients; the mechanism is described in §3.2.3.5. Two error paths are defined explicitly. A file that cannot be decoded produces a per-file error entry in the results and the batch continues, so that one unreadable file cannot abort a scan. And a heatmap whose values are uniform, which can occur with a degenerate input, is not normalized but skipped, so that the source image is shown uncolored rather than the calculation failing.

#### 3.2.3.5 Model Export Interface and Preprocessing Parity

The exported model exposes four outputs in a single forward pass, and this interface is what allows the application to produce a heatmap without a second computation. The first output carries the class logits, from which the verdict and probability are derived; the second carries the final convolutional feature map before global pooling, which the heatmap requires; the third carries the classification head's weight matrix, emitted directly at export time; and the fourth carries the head's bias, exported for completeness and for the parity checks. Because the head is a global average pooling layer followed by a linear layer with no convolution after pooling, the row of the weight matrix corresponding to a class is exactly that class's set of heatmap weights, so the heatmap costs no additional forward pass. The export step asserts this precondition and fails rather than producing a model that cannot support the heatmap. Training in Python and deploying into a native application is the pattern documented by the runtime used here ([ONNX Runtime, n.d.](https://onnxruntime.ai/docs/)).

**Table 3-4.** Outputs of the exported model, produced in a single forward pass.

| Output | Shape | Purpose |
|---|---|---|
| Logits | 1 × 2 | Verdict and class probability after softmax in the application |
| Feature map | 1 × C × H × W | Final convolutional features before global pooling, used for the heatmap |
| Head weights | 2 × C | Classification head weight matrix; row *c* is class *c*'s heatmap weight vector |
| Head bias | 2 | Classification head bias, used for parity checks |

Preprocessing is implemented twice, once in Python for training and validation and once in Rust for the application, and the two implementations are kept in agreement by two mechanisms. The constants that define the input convention — the target size, the channel order, the normalization statistics, and the class order — are held in a single documented place that is mirrored into both codebases, so that there is one authority for each value rather than two. And a parity test compares the tensor produced by the Rust path with a tensor produced for the same image by the Python path, under a documented per-element tolerance, and additionally requires the two paths to agree on the verdict and probability for each sample image. Exact pixel equality between two independent image resamplers is not claimed, and the tolerance exists precisely because bilinear resampling is not implemented identically in the two libraries; what the test establishes is that the difference is small enough not to change a prediction.

#### 3.2.3.6 Persistence Schema

The application keeps no database. Screening results are persisted to a single JSON document in the application's data directory, written atomically by writing a temporary file and renaming it, so that a crash during a write can lose at most the entry in flight and cannot corrupt the store. All screening paths — single images, manual selections, and batch scans — append through the same writer, and the store is capped at 500 entries, with the oldest entries evicted first and an explicit clear operation always available. Each entry records the raw probability rather than only the derived verdict, together with the threshold that was applied, so that a stored verdict remains re-derivable if the operating point is ever changed. Heatmap images are not persisted: the detail view recomputes the heatmap on demand, and only when the source file still exists and the entry was produced by the model version currently bundled, so that a heatmap can never be shown beside a verdict it did not explain.

| Field | Type | Purpose |
|---|---|---|
| `id` | String | Unique identifier of the screening entry |
| `timestamp` | String | Date and time of screening |
| `source_path` | String | Full path of the screened image on the local machine |
| `file_name` | String | File name of the screened image |
| `verdict` | String | Binary label displayed for the image (tumor or no tumor) |

### 3.2.4 Evaluation

Evaluation is conducted in two parts that correspond to the two claims the study makes: that the trained model performs acceptably on data it has not seen, and that the application performs the functions specified for it.

The first part evaluates the model on the held-out test partition, using the partition set aside after training and tuning, on which the final performance measures are calculated ([Hicks et al., 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8993826/)). The reported measures are derived from the counts of true positives, true negatives, false positives, and false negatives ([Hicks et al., 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8993826/)): accuracy, which is the proportion of correctly classified images; precision, the proportion of images labeled tumor that are tumor; recall or sensitivity, the proportion of tumor images correctly identified; specificity, its negative-class counterpart, defined as the percentage of true negatives among all subjects who do not have the condition ([Shreffler & Huecker, 2023](https://www.ncbi.nlm.nih.gov/books/NBK557491/)); the F1 score, the harmonic mean of precision and recall, which penalizes extreme values of either measure ([Hicks et al., 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8993826/)); the area under the receiver operating characteristic curve, which summarizes the model's ability to distinguish between classes across all thresholds and is reported with its confidence interval ([Çorbacıoğlu & Aksel, 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10664195/)); and the confusion matrix itself. Accuracy is reported alongside the other measures rather than as the sole headline figure, because it is known to be misleading when class proportions differ ([Hicks et al., 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8993826/)), which is the case for the collapsed dataset used here, and every measure is reported both overall and separately for the two contributing sources so that strong performance on the larger source cannot conceal weak performance on the smaller one.

The decision threshold is selected on the validation partition and never on the test partition. The selection maximizes the Youden index, the value that maximizes a test's sensitivity and specificity, subject to a sensitivity of at least 0.95 where that is attainable, with any shortfall recorded; the Youden index and the requirement that a confidence interval accompany the reported area under the curve both follow the guidance for interpreting diagnostic accuracy ([Çorbacıoğlu & Aksel, 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10664195/)). The sensitivity constraint reflects the system's intended role as a pre-screening filter, in which a missed tumor is the more expensive error and the clinician, not the model, makes the final decision ([Chen et al., 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11608314/)). The selected threshold is stored in the model's configuration record and shipped with it, and every stored result retains the probability and the threshold that produced its verdict.

Acceptance for this part of the evaluation is a predetermined bar of at least 95% accuracy on the held-out test partition. The method used to reach it is transfer learning from a pre-trained backbone, which can provide better accuracy even when the number of available training samples is small ([Rasa et al., 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11459499/)), supplemented by data augmentation, which the reviewed literature applies both to reduce overfitting and to address class imbalance ([Rasa et al., 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11459499/); [Khan et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12149374/)). If the bar is not met, the response is to iterate on augmentation and architecture and to report the achieved figures, with any change to the acceptance bar documented and justified rather than applied silently.

The second part assesses the functional suitability of the prototype, which is used in this study to mean the degree to which the application performs its specified functions correctly under test. Each core function is exercised by a test case stating its preconditions, the steps taken, the expected result, and the observed result, and each case is recorded as passed or failed. The functions covered are the loading of a single image, the scanning of a folder batch with live progress reporting, the display of the verdict, confidence score, and threshold including the low-confidence band, the generation and display of the heatmap overlay, the persistence of history across application restarts, the export of the CSV summary, the export of annotated image copies, the handling of an unreadable file without aborting a batch, and the visibility of the disclaimer. Two further checks support this part. The parity test described in §3.2.3.5 is treated as a correctness test rather than as a development aid, since it verifies that the shipped inference path reproduces the behavior of the model that was evaluated. And the heatmap is inspected qualitatively on at least ten known-tumor images from the test partition, to confirm that the highlighted regions correspond to the lesion rather than to background or non-tumor tissue, which is recorded with the images and notes in the project repository.

The scope of this evaluation must be stated as plainly as its content. The heatmap check is a qualitative inspection, not a measure of explanation fidelity, and this study does not measure whether the heatmap is trusted or useful to the person reading it; the same meta-analysis that motivates the study's user-facing design reports that explanation fidelity, clinician trust, and usability in real settings remain largely unevaluated in this literature ([Abbas et al., 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12427955/)), and that limitation is inherited here rather than resolved. More generally, because the model is trained and tested on public benchmark images partitioned internally, the evaluation establishes internal performance only: no external, multi-center, prospective, or clinical validation is performed, scanner and protocol variation is uncontrolled, and the system's output is a screening label rather than a diagnosis. These delimitations are the same ones that apply to the comparable systems reviewed in §2.2, and they define the sense in which the results are reported.
